Papyrus Import Pipeline Audit

2026-08-16 working tree @ build v194 (1.5.9) vs release 2415d70 (1.5.8) evidence: full-source read · git archaeology · on-device forensics

UPDATE — root cause found and fixed. The single biggest cause was F16: concatArray, the engine’s most-used primitive, was quadratic. It filled backwards, writing past the end of the destination array first, which permanently degraded every accumulating byte buffer into a sparse/dictionary array. Measured cost of accumulating 1.3MB in 4KB pieces: 58.5 seconds backwards versus 31 milliseconds forwards (~1900×). Because the penalty scales with how much has already been accumulated, small books were fine and large ones appeared to hang — the exact content-dependent behaviour that made this look nondeterministic. All findings below stand; this one explains the magnitude.

Why does the same book import in 90 seconds on one run and 10–25 minutes on another? Two compounding answers. First, a quadratic core primitive (F16) made cost explode with book size. Second, the import engine could not be stopped, could not report its own failures, and could not detect a competitor — so every abandoned, timed-out, or repeated import kept running invisibly, stacked on top of the next one. On top of those sit several book-dependent pathologies inherited from different eras of the codebase. This was not one bug; it was an architecture that turned every small problem into a nondeterministic one.

§1How the pipeline actually works

Every import is a chain of thousands of tiny steps connected by Function.prototype.defer() — which in this app is setTimeout(fn, 10) (MojoCompat.js:269). The chain has four phases:

PhaseWhat runsDefer-linked steps (Star Trek book)
1. Load + unzipFile (100ms polling) → ZipFile parse~2
2. Parse ePubEpubReader: OPF → per-entry Inflate (defer per DEFLATE block) → filterMarkup — all 22 chapters filtered as concurrent interleaved chains, 4KB per step~250
3. Coverdecompress + btoa + canvas thumbnail~40
4. StoreHTMLBook: 16KB read → re-parse → base91 → one WebSQL transaction per chunk + per image~80 steps, ~40 transactions

Implications that matter for everything below: at a 10ms timer floor, ~400 defers is a 4–20 second tax before any real work; every other consumer of the JS thread or the WebSQL queue directly stretches the chain; and no step has a try/catch, a cancellation check, or an owner that knows whether it is still wanted.

§2Why the same book takes 90 s, 10 min, or 25 min

The variance is not one branch misfiring — it is the compounding of independent multipliers on a pipeline with no isolation:

  • Zombie chains (F1). Nothing ever stops an import. Watchdog “timeout,” navigating away, opening a book, starting a new import — the old chain keeps running to completion, minutes later. Two interleaved chains > 2× slower each (defer queue doubles, transactions serialize). Device evidence: today’s “abandoned” runs all have completed DB files with late mtimes.
  • In-app activity (F11). The user opened and read books during imports (confirmed in logs at 16:39). PageFitter’s binary search runs dozens of layout/DB operations on the same thread and same WebSQL queue.
  • Silent failure (F2). One uncaught exception anywhere in a chain kills that chain with no error — the UI shows the last phase forever. What looks like “slow” is sometimes “dead.” (The Mad Libs bug at the start of this session was exactly this class.)
  • Flash/fsync variance. ~40 WebSQL transactions × 50ms–1s+ each depending on competing I/O.
  • Test-environment noise (F12). Stale code served without a Luna restart, system log level left at info (my doing — revert it), and two different devices used across today’s A/Bs. Several of today’s data points are unreliable.

The one clean measurement — fresh device, fresh launch, 1.5.8, nothing else running — was 90 seconds. Static analysis of the current OFF-path shows byte-for-byte the same work as 1.5.8 plus ~5s of cover handling. Any observed gap beyond that on a given run is environmental, and the architecture currently has no defenses against any of it.

§3Findings

F16 concatArray was quadratic — the core slowdown critical FIXED

src/io/Bytes.js concatArray — used by chapter output, plain-byte buffers, inflate output, tag buffers, everything

The old implementation appended by filling backwards: it wrote arrayTo[newLength-1] first and worked down. That first write lands far past the array’s end, punching a block of holes, which makes the JS engine abandon the packed-array representation for a sparse/dictionary one — permanently, on an array that only grows. Every subsequent byte append then costs a hash-table operation.

accumulatedbackwards (old)forwards (new)ratio
82 KB108 ms3 ms36×
328 KB2,344 ms6 ms390×
655 KB12,557 ms12 ms1,046×
1.3 MB58,512 ms31 ms1,887×

Why it looked nondeterministic: the penalty is a function of bytes already accumulated, so it is invisible on a short book and catastrophic on a long one — and it interacts with anything that changes chunking (which is why toggling chapter breaks appeared to matter so much). Fixed by appending forwards, which keeps the array packed and is linear; semantics unchanged. A 279KB pathological chapter went from 2,016 ms to 222 ms in-harness, and scaling is now proportional instead of quadratic.

F1 Imports cannot be cancelled — zombie chains critical FIXED

Main.js:951–969 · FileImporter.js (all paths) · EpubReader.js / HTMLBook.js / Inflate.js (no abort anywhere)

The watchdog “abandons” a stuck import by setting importCallbackFired = true and walking away — the chain itself keeps deferring, parsing, and writing until done. There is no code path in the entire engine that stops a running chain. Every abandoned run competes with subsequent runs for the thread and the DB. This is the primary driver of run-to-run variance.

F2 No error propagation: any exception = silent forever-hang critical FIXED

every .defer() site · MojoCompat.js:34–66 (Synchronize)

Chain steps run inside bare setTimeout callbacks with no try/catch. A thrown exception vanishes; the chain dies; Synchronize.pendingCount never reaches zero; the callback that would report success or failure never fires. The UI sits on the last phase message until the watchdog gives up (or forever, once contentProcessingStarted is true — that branch retries the watchdog indefinitely). Both “hung” books this session (Mad Libs, Goosebumps) were this exact failure shape.

F3 No re-entrancy guard on import major FIXED

Main.js:875 importMultipleEpubs

Tapping Import while an import runs starts a second full pipeline concurrently. Combined with F1, an impatient user (facing a stuck-looking spinner) manufactures their own slowdown.

F4 Watchdog timeout stalls the multi-book queue major FIXED

Main.js:959–968

The pre-content timeout path increments current but never calls importNext() — the rest of a multi-select import silently never happens, and blockScreenTimeout handling ends early while the zombie continues.

F5 “Timed-out” imports still add themselves to the library later major FIXED

FileImporter.js:183 saveBookMetadata (unconditional)

The library write happens inside FileImporter before the (now-ignored) callback. A zombie that eventually completes inserts its book with no view refresh — phantom entries that appear on next launch.

F6 Orphaned database leak on every re-import major FIXED

FileImporter.js:132,167 (generateUniqueId embeds Date.now()) · saveBookMetadata replaces entry without deleting the old DB

Confirmed on device: 30 DB files, 107 MB, with duplicate-size clusters (three 7.2 MB copies from May 25; three 3.86 MB Star Trek copies from today alone). Re-importing a book replaces its library entry with a new bookDbName, stranding the old full-content DB forever. WebSQL offers no enumeration API, so existing orphans are unreachable from JS — only new discipline (delete-before-reimport + a dbName registry) prevents growth. Bonus defect: asin and bookDbName call generateUniqueId separately and get different timestamps.

F7 Quadratic re-parse when a tag spans the 4KB filter boundary major book-dependent

EpubReader.js filterChapter: chunk-carry at ~line 799 vs. parse of full extraBytes each round

If a tag doesn’t close within the current buffer (giant inline style, base64 data-URI in an attribute, unterminated comment — classic “quirky book” material), the dropped tail is carried and the entire accumulated buffer is re-parsed every 4KB round. A tag that never closes within the chapter re-parses an ever-growing buffer ~115 times for a 470KB chapter — minutes of invisible work, per chapter, labeled “Parsing ePub…”.

F8 Silent book truncation on any tag > 16KB major FIXED

HTMLBook.js:278–281 (“document ends malformed” branch)

In the storage pass, a single tag longer than one 16KB chunk (data-URI images survive filtering verbatim inside img label) makes byteBuf.length - dropped ≤ 0, which is treated as end-of-book: finish() runs and everything after that point is silently discarded. The import “succeeds,” the book is incomplete.

F9 Chapter-boundary chunking looked 10–20× slower — it was F16 major RESOLVED

HTMLBook.js · gated by chapterPageBreaks

Static analysis said +27% read/write cycles; the device said 10–20×. That gap was the clue, not the noise: the extra chunking simply pushed more work through the quadratic concatArray (F16). With F16 fixed the harness shows identical work either way (Star Trek 474 steps / 18 writes with breaks on or off), and the feature is on by default again.

One design bug shipped briefly along the way: the preference gated whether boundaries were recorded at import as well as whether they were displayed. Boundaries live in the book’s stored metadata, so a book imported with the preference off had none and enabling it later did nothing until re-import. Recording is now unconditional; the preference controls display only.

F10 Unclosed-tag baggage compounds through the whole book minor book-dependent

HTMLBuffer.js (openTagsEnd carried + serialized per buffer) · HTMLParser.addToOpenTagArray

Tags that never close (books full of unclosed <div>s pass through the filter) accumulate in openTagsEnd, are cloned per chunk, scanned per closing tag, and serialized into every subsequent buffer record — a per-chunk cost and storage bloat that grows as the book progresses. Matches the observed “starts fast, decelerates” shape for some books.

F11 Everything shares one thread and one DB queue by design design tax

MojoCompat.js defer (10ms floor) · filterMarkup’s N-concurrent chains · PageFitter/Sync during import

~400+ defers per import is a 4–20s floor before work. The 22-way concurrent chapter filtering (a pReader-era choice) maximizes interleaving with anything else running. Reading a book mid-import runs pagination binary-searches against the same WebSQL origin. None of this is a bug alone; it is the amplifier for F1/F3.

F12 Test-hygiene contaminants in today’s measurements note

webOS serves stale cached app code unless a Luna restart follows install (your rule; several of today’s installs got no restart). --system-log-level=info was left on for at least one device (adds system-wide log I/O; I will revert it). Two different devices were used across A/Bs. Conclusion: only the fresh-device 1.5.8 run (90s) and future instrumented runs should be treated as ground truth.

§5Remediation plan

Ordered so each phase de-risks the next. Nothing below touches parsing behavior until measurement exists.

P0 — Instrument before touching anything

  • One summary log line per import: per-phase wall time, chunk count, transaction count, defer count, bytes. Every future regression becomes diagnosable from a single line instead of a session like today’s.
  • Revert device log level to error; re-baseline the Star Trek book on a clean launch.

P1 — Make imports killable and honest (fixes F1–F5)

  • Import session token: one object threaded through EpubReader/HTMLBook/Inflate; every chain step checks session.cancelled and exits. Cancel on: watchdog timeout, new import, returning to library during import, app close.
  • Import lock: importMultipleEpubs refuses while a session is live.
  • Fail-fast errors: try/catch at the defer trampoline → session.fail(err) → the one callback, always called, success or failure.
  • Fix the queue stall; make saveBookMetadata conditional on a live session.

P2 — Pre-flight + hygiene (fixes F6, arms against F7/F8)

  • Pre-flight after OPF parse (cheap, all metadata already in hand): chapter count and sizes, image count/sizes, largest single tag risk (scan for data: URIs). Decide strategy per book: image skip list, warnings for books that will truncate, honest time estimate.
  • Delete the old DB before re-importing the same book; keep a dbName registry in localStorage so future orphans are findable and purgeable.
  • Negative-cache skipped images (F13).

P3 — Performance, only once P0 can prove it

  • Time-sliced trampoline: run chain steps synchronously up to ~50ms, then yield once — cuts the 400-defer tax ~10× while keeping the UI alive.
  • Batch buffer writes through the existing writeBatch().
  • Done. Chapter-boundary chunking (F9) re-evaluated with clean instrumentation: the cost was F16, and the feature is back on by default.
  • Fix F7 (carry only the partial-tag tail, don’t re-parse the prefix) and F8 (stream giant tags instead of truncating) — correctness wins that also remove worst-case cliffs.

§6Open questions

  • F9’s true mechanism — unresolved until a clean instrumented A/B exists.
  • Whether webOS throttles background-card timers (would make backgrounded imports crawl by OS policy) — testable with P0 instrumentation and a deliberate background run.
  • Whether existing orphaned DBs can be reclaimed at all from JS (likely not; may warrant a one-time novacom cleanup script for affected devices).
